Accessibility statement for this prototype

We are committed to digital inclusion and have built this click dummy prototype with deep respect for accessibility standards. This statement outlines the measures implemented specifically within this demonstration slice to support assistive technologies and keyboard-only operation.

Note: This accessibility audit applies specifically to the static HTML, CSS, and JS files contained in this frontend prototype. Ongoing WCAG compliance monitoring will be maintained as the app transitions to a fully connected cloud application.

Implemented Accessibility Measures

1. Semantic Landmarks

Every page is structured using native HTML5 structural landmarks: <header>, <nav>, <main>, <section>, and <footer>. Each page is restricted to a single descriptive, high-level <h1> heading, with subsequent headings matching a logical hierarchical tree. A "Skip to main content" bypass link is instantly available upon initial keyboard tab index engagement.

2. Robust Keyboard Operation

All interactive elements—including anchors, buttons, form controls, tab panels, and overlay triggers—are fully keyboard-tabbable and operable. Buttons can be activated using Space and Enter, and standard ARIA keyboard bindings have been custom-implemented.

3. Visible Focus Indicators

No focus styles are disabled. All interactive elements feature a highly visible, contrasting custom focus outline ring (--focus-ring: #27386c) offset by several pixels to ensure high legibility.

4. OS and Manual Reduced Motion

We respect user preferences regarding animation. In addition to listening directly to the system-level prefers-reduced-motion media query, we have integrated a keyboard-accessible global header toggle labelled "Reduce motion / Enable motion." When activated, all SVG line drawings, card hover transformations, and fade transitions are immediately disabled, leaving a completely static layout.

5. Explicit Form Labels and Programmatic Errors

All input fields are bound to persistent, visible text labels (no hidden labels or placeholder-only identifiers). Submission errors are programmatically linked to fields using aria-describedby attributes, and a dedicated, accessible Error Summary panel receives focus upon a failed form submission, allowing screen-reader users to easily jump to specific faulty fields.

6. Modal Dialog Focus Containment

The Evidence dialog implements a complete role="dialog" pattern. When opened, focus is programmatically shifted inside, trapped within the modal borders while open, and can be dismissed using the Escape key, clicking the background, or activating close buttons. Focus is restored to the triggering button upon exit.

7. Symmetrical, Responsive Reading Order

Our mobile layout uses CSS-based flex and grid orders to ensure that the relationship-first reading flow matches the visual reading order. Screen-readers encounter elements logically from "Shared Dynamic" to "Person A" and "Person B" without requiring DOM duplication.
